## Outcome

A developer starts the basic platform with Docker Compose, opens the same-origin Console, establishes
their administrator session, configures one or more model sources, tests a connection, selects a
default model and runs an Agent. CLI users and automation perform the same operations through the
same public management API. Kubernetes installations consume the same owning configuration and
initialization semantics through Helm. Sandbox retains the existing Kubernetes/OpenSandbox boundary.

## Ownership

- Deployment owns physical endpoints, workload identities, TLS, process configuration and artifact
  identities. A management request cannot install a network destination or modify a process file.
- Registry owns model providers, model profiles, their revisions/deployments and selection policies.
  A source is the product name for an existing ModelProvider resource, including separate accounts
  or regions from the same vendor. Vendor identity does not determine protocol or environment names.
- Security owns SecretBinding creation, rotation, revocation, current authorization and audit.
  Secret Broker owns bounded external credential preparation and reference encryption; raw keys
  never enter resource documents, Receipt projections, command events or deployment manifests.
- PostgreSQL owns durable commands, aliases/default selection, concurrency and recovery. Any alias
  representation must attach to its existing owning resource or tenant configuration, not introduce
  a parallel source/model database.
- Console and CLI are public clients. Shared application operations remain server-side. A product
  convenience operation must retain ordinary Registry validation/publication and Security checks.

## Deployment

The basic Compose closure includes the Console transport, both Gateway roles, orchestration,
Registry validation, required Artifact roles, outbox/history workers and selected model/context
roles. Each role is its own process/container with its own config and bounded pools. No container
mounts a Docker/CRI socket. Local dependencies and any shared development trust are explicitly
non-production. Only the Console ingress and explicitly required browser object transport are
published to the host; internal endpoints remain within the installation.

One-shot initialization prepares deployment inputs and invokes the existing fresh-schema and
bootstrap owners. Provisioning and running use separate commands. Serving processes never provision,
migrate, reset, repair or silently overwrite persistent state. A restart verifies persisted identity
and resumes permitted platform provisioning with that same identity. Initial provider self-init has
a one-time start permission: an incomplete or unknown result preserves the original volume and
cannot be automatically restarted or repaired. Exact provider authentication and readback establish
ProviderReady before platform resume is allowed. Credentials and databases are not replaced.
Concurrent initialization serializes using the owning guards; ambiguous external writes require
exact readback.

The shared Rust renderer preserves actual worker build identities and canonical digests. Native,
Compose and Helm consume that owner rather than duplicating role configuration in shell, Python,
Helm templates or TypeScript. Each deployment tool owns process startup, rollout and shutdown.

Console remains a static application behind a transparent same-origin router. The router preserves
Authorization, Receipt, ETag and SSE semantics, imposes bounded transport limits, and owns no business
state. Authentication uses the existing OIDC verifier. New local installations explicitly bind a
tenant administrator and deliver a short-lived token in a private file; renewal is an explicit
session operation. An unprotected first-request-wins administrator endpoint is forbidden.

## Model configuration

The public surface covers available installed destinations, source create/read/list/update,
credential import/rotation/revocation, model create/read/list/update, connection test and explicit
default model selection. Source identity, wire protocol, physical endpoint, credential binding and
provider model identity are separate facts. Multiple sources may use one vendor; multiple models
may use one source. There is no implicit fallback between configured credentials or providers.

Client environment import accepts explicit variable names per input, plus documented vendor presets.
An explicit mapping wins over a preset. Only named variables are read; missing, empty and conflicting
inputs fail with safe field/variable names. Never scan the environment for candidate secrets. Import
is an explicit operation, not runtime credential lookup. The same input model supports mounted secret
files in unattended deployments and a transient password field in Console.

SDK base URLs are normalized by the shared owning parser into the installed protocol's endpoint
representation, including the `/compatible-mode/v1` Responses case. Userinfo, query, fragments,
ambiguous path encodings and unsupported schemes are rejected. Deployment allowlists, DNS pinning,
public-address checks, TLS verification and redirect rejection remain enforced at Egress.

The source registration flow must resolve the ordering between physical installed destinations and
server-assigned exact Provider deployments without allowing callers to choose arbitrary outbound
addresses or fabricate IDs. Credential rotation creates a new exact binding identity; existing Runs
retain their frozen dependency closure and remain subject to current authorization/revocation.

Model registration distinguishes operator-declared limits, verified adapter support and measured
provider evidence. An HTTP 200 or one successful text completion cannot establish tokenizer,
streaming, tool, structured-output, identity-stability, retention or training claims. Only supported
and evidenced capabilities can be advertised. Basic registration uses operator-declared limits,
locally verified protocol support and explicit unknown provider facts; it does not manufacture
provider qualification or a retention/training guarantee.

Connection tests use the real installed Egress and Secret paths with bounded input, response, time
and concurrency. Results expose safe protocol outcomes, never credentials or raw
provider errors. A test creates no Agent/Run qualification claim. Full model execution continues
through the existing ModelLoop, budgets, permissions, fencing and exact dependency resolution.

Default selection belongs to the current tenant/selection owner. Changes require current permission
and optimistic concurrency; simultaneous updates cannot silently overwrite each other. Existing Runs
keep their frozen selection. No source deletion or model change automatically reroutes another model.

## Reviewed work and acceptance sequence

The contract review and implementation steps below have been carried out for the implemented
slices. Their targeted evidence is recorded in the linked reviews. The last physical and full
business scenarios remain open as listed above; this sequence is not an all-passed checklist.

1. Review the ADR and owning public/process/persistence contracts together: identities and aliases,
   permissions, bounded schemas, safe error codes, Receipt/ETag behaviour, external-write recovery,
   secret handling, endpoint installation, quotas, capability evidence and first-use authentication.
2. Implement shared deployment generation and one-shot initialization; provide complete Compose and
   Helm wiring, health checks, dependency ordering, same-origin Console serving and scoped cleanup.
3. Implement source/credential/model/default application operations and public transport; generate or
   validate machine representations from the owning Rust types and preserve current boundaries.
4. Implement CLI environment/file import and all management commands against that API.
5. Implement Console setup and source/model management, connection results and default selection.
6. Validate real dependency startup, first use, model invocation, restart, credential rotation,
   concurrent mutations, failed initialization recovery, access denial and secret redaction.
7. Update current usage/operations documentation and examples; cross-review implementation/evidence,
   run affected repository checks, then remove this temporary proposal.

## Required evidence

- Clean Compose startup from documented inputs and a usable same-origin Console; no host Cargo/Node
  requirement when consuming built images, and no CLI supervisor hidden inside a service container.
- Two sources from one vendor and another protocol coexist without key, alias or default collisions;
  arbitrary environment mappings work and error paths never disclose secret values.
- Current authorization before replay/read, tenant isolation, stale ETag rejection and concurrent
  default/credential changes. An uncertain external secret write is resumed by exact identity.
- Real model call through Platform Egress/Secret/ModelLoop with truthful model capability metadata;
  streaming and structured/tool features are individually qualified only if enabled.
- Restart preserves identity, credentials, default selection and existing business data; a failed
  bootstrap never resets them. Serving processes fail on incompatible schema/configuration.
- Helm render and deployment checks consume the same reviewed semantics. Local cluster proof remains
  separate from production qualification. Sandbox remains an explicitly selected Kubernetes path.
- The documented sample includes retrieval and human approval using real dependencies; a human
  response must come from the user, and cannot be manufactured by the test harness.
